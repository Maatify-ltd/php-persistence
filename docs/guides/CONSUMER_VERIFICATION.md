# Consumer verification and coexistence

From a checkout of the committed candidate, run `composer test:consumer` with PHP 8.4 or newer (PDO MySQL enabled), Composer 2.10, Git, cURL, tar, and Docker Compose. Internet access is needed for Composer dependencies, the pinned legacy source archive, and the Integration database image. `CONSUMER-ARCHIVE` records the committed HEAD, its tree and the SHA-256 of its Git archive. Pull-request CI uses the PR HEAD. For the published package use the [RC.2 quickstart](USAGE_GUIDE.md#run-the-published-rc2-examples-from-a-clean-install).

The required CI job provisions two fresh services for MySQL 8.4.13 and two for MariaDB 11.8.9 through the existing Integration lifecycle. Set `PP_DB_CELL` to select the cell when running locally. Each service runs both scenarios in independently generated Composer roots outside the repository. Every root starts without a lock, vendor, or project state and installs both packages through Composer with `--no-dev`. It runs the repository's dependency policy, uses only the production autoloader, and verifies the installed package identities. The candidate is mirrored from the Git archive. The consumer project owns its schema and input catalog fixtures. Each lifecycle verifies zero tables and open transactions, removes the consumer directories, and verifies Compose teardown.

| Scenario | Legacy identity | Evidence |
|---|---|---|
| Coexistence | Published `maatify/persistence:1.4.0` at `fc1459b49fe5af5ead17814eeb3ada7a3fa81791` | Dist reference checked in Composer lock. Both savepoint runners resolve to separate types. On one PDO connection, each package takes its turn as the inner savepoint runner. Rolling back the inner operation preserves earlier caller and outer-runner writes. The caller can still roll back both packages' work. The candidate also executes the catalog workflow. |
| Differential | [Unpublished legacy source](https://github.com/Maatify/persistence/tree/1f6a7aafe601090b7e55f60d83794364afdefe67) | Exact source archive installed in its own consumer root alongside the candidate. The same fixture, assertions, and observable pagination results apply to both packages. |

After each scenario passes, the harness copies the [Basic examples](USAGE_GUIDE.md#run-the-published-rc2-examples-from-a-clean-install) and the candidate's C1, Keyset, Verified Apply/Discard, static sort and dynamic sort examples from the installed candidate. It checks each example and the shared bootstrap against the Git archive before execution. Every example loads that consumer root's production autoloader. The [C1 example](../../examples/pagination_snapshot_usage.php) checks session reuse after confirmed settlement on success and mapper failure and checks the original exception's identity.

Each production Composer root also checks the installed Keyset signatures and exception marker, then runs the [Keyset example](../../examples/pagination_keyset_usage.php) from the installed archive. It reads two pages and checks the continuation, terminal JSON and cursor rejection for a different Host scope. Keyset is verified on the candidate in this scenario.

## Coexistence audit

[DEC-016](../decisions/DEC-016-legacy-coexistence-abandonment-audit.md) allows an audit-only abandonment ignore for the published legacy fixture in the temporary coexistence project. The harness first installs with the default policy, checks platform requirements, and verifies that the production lock identifies `maatify/persistence:1.4.0` with dist reference `fc1459b49fe5af5ead17814eeb3ada7a3fa81791`. Composer matches abandonment ignores by package name, so the harness checks this exact version and reference before adding the rule. It runs `composer audit --abandoned=fail` with the rest of the policy intact. The differential project and other audits use the standard policy.

## Behavior evidence map

The [behavior contract](../architecture/BEHAVIOR_CONTRACT.md) labels published legacy as A, unpublished legacy as B, and this package as C.

| Behavior | Evidence and limits |
|---|---|
| B-01, B-02, B-03, B-06, B-07 | Differential catalog exercises scoped/nullable allocation, a locking allocation followed by insert in the same transaction, a clamped move, no-op and missing moves, and soft-delete/row visibility. B-02 and the B-03 locking-snapshot change use B as the source baseline. For both packages, a second connection commits a new maximum after the caller establishes its InnoDB repeatable-read snapshot. The plain read retains the old maximum and the locked move clamps to the newly committed maximum. Fine-grained lock footprint stays covered by the repository's Integration suite. |
| B-04 | Published and source coexistence scenarios prove nested savepoint isolation through transaction runners. The differential catalog also triggers a CHECK constraint failure after a range shift and proves local rollback preserves earlier caller work against B. The remaining Ordering-specific lazy rollback branches stay covered by `ScopedOrderingManagerLazySavepointTest` and `ScopedOrderingManagerSavepointWiringTest`; it is a documented delta from A. |
| B-05, B-10, B-13 | The catalog checks owned commit/rollback, move return values and callback exception identity against B. Fail-closed PDO control failure behavior is an approved delta from A and remains exercised by the named repository tests. Exception FQCNs and the package marker differ. |
| B-08, B-08a, B-09 | Differential catalog compares pagination normalization, filtering, ordering and the result envelope. A second real connection commits between the two count queries without timing sleeps. Autocommit can observe inconsistent counts and caller-owned InnoDB repeatable read gives a single snapshot. The PHP DTO name changes while the observable array and JSON payloads agree. |
| B-11, B-12 | Nested savepoints are checked in both directions against both legacy identities. A separate differential fixture uses the two Gen2 runner forms in each package with one configured retry. A bounded pipe handshake and two conflicting InnoDB row locks produce a real `40001/1213` victim. Each form replays once inside a fresh transaction and commits only the second attempt. Retry is a delta from A. Retry exhaustion and fail-closed paths remain covered by `DeadlockRetryIntegrationTest` and `DeadlockRetryFailClosedTest`. |
| B-14, B-15, B-16 | Harness SQL and transactions execute on the two named engine cells. Existing Integration and compatibility jobs remain required. Engine evidence, Composer constraints, and archive scope remain distinct. Exact release artifact verification belongs to WU-11. |

The orchestrator is checked by the package's PHPStan configuration. The independent consumer fixture is syntax-checked and validated through execution in the two production Composer roots, where its legacy imports resolve.

The harness is additional to Unit, Regression, Integration and Examples Smoke. This evidence concerns a candidate tree before publication. It provides neither production host migration evidence nor a support-range claim. The harness also exercises the protected write checkout in DEC-009, and DEC-013 records test versions.
